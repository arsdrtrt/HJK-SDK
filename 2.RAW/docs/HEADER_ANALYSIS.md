# Результаты анализа — разбор

Захват отработал идеально: **ровно 500 кадров, 327 680 000 байт** — off-by-one фикс сработал. Теперь к сути.

## Что показывают данные

### Три фазы поведения сенсора

| Фаза | Кадры | Среднее | Шум | Что происходит |
|---|---|---|---|---|
| Прогрев | 0–2 | 13252 → 12191 | 3634 count | Первый shutter, NUC применяется |
| Первая стабильность | 3–128 | 12194 | **9 count** | Чистая серия, 126 кадров |
| Турбулентность | 129–207 | 12411 → 12783 | 100–232 count | Движение в кадре / второй shutter / помеха |
| Стабильность | **208–499** | 12190 | **9.76 count** | 291 кадр, идеальный участок |

**Кадры 129–207** — не «плохие данные», а **реальные события**: колебания на 500+ count (5 °C) с высоким std. Это либо движение объекта в поле зрения, либо несколько shutter'ов подряд. Их надо игнорировать.

### NETD — первая оценка

```
Длиннейший стабильный сегмент: 208..499, 291 кадр (11.6 с)
temporal noise, median:          9.76 count = 0.098 °C
temporal noise, mean:           18.71 count = 0.187 °C
temporal noise, 90th percentile: 21.66 count = 0.217 °C
```

**NETD ≈ 98 mK** (по медиане), **~190 mK** (по среднему).

Разброс median vs mean — критичен: половина пикселей имеет шум ~10 count, но 10% имеют >21. Это **битые пиксели + остаточный FPN после NUC**.

| Сравнение | NETD |
|---|---|
| FLIR Lepton 3.5 | <50 mK |
| HIKMICRO Mini2 | <40 mK |
| **Наша камера (по Y16)** | **98 mK** |
| Типичный китайский microbolometer | 50–100 mK |

Результат **в рынке**. Но: это **системный NETD**, не сенсорный. NUC/DPR уже подавили часть шума. Реальный сенсор хуже.

### Что сказать про «до NUC»

Из данных ясно: **Y16 — после NUC**. Доказательства:

1. Кадр 0: max = **56317** (hot pixel 462 °C). Кадр 2: max = 13406. NUC **подавил** выбросы.
2. После каждого shutter baseline сдвигается (12194 → 12411 → 12783 → 12190). Это NUC-обновление.

Значит пункт 4 из твоего плана (доступ до NUC) — **скорее всего недоступен**, надо фиксировать это и работать с радиометрическим Y16.

```bash
# Разбор структуры потока Y16

## Что приходит в callback

SDK отдаёт `Frame*` со следующими полями (из `IRSDK.h`):

- `width`, `height` — размеры (640 × 512)
- `buffer` — указатель на `uint16_t[640*512]`
- `u16FpaTemp`, `u16EnvTemp` — заглушка, всегда `12000`
- `u8TempDiv` — делитель, обычно `100`
- `u8MeasureSel` — диапазон, `0` в нашем случае

**Заголовка в буфере нет.** Первые байты `raw16.bin` — сразу пиксели.
Проверено: `head -c 64 raw16.bin | xxd` показывает непрерывные Y16
значения (~13100), никаких magic/version/размера.

## Итоговая раскладка `raw16.bin`

```
┌──────────────────────────────────────┐
│  Y16 пиксель (0,0)   uint16 LE       │  offset 0
│  Y16 пиксель (0,1)   uint16 LE       │  offset 2
│  ...                                 │
│  Y16 пиксель (511,639) uint16 LE     │  offset 655358
│                                      │
│  Далее следующий кадр (без разрыва)  │  offset 655360
└──────────────────────────────────────┘
```

Размер одного кадра: `640 * 512 * 2 = 655 360` байт.

## Что НЕ приходит в callback

`tagFrame` (32-байтный заголовок из `IRSDK.h`) **не передаётся**. SDK
отдаёт только `buffer` — саму матрицу пикселей. Поля `u32FrameIndex`,
`u8Fps`, `u8TriggerFrame` заполняются заглушками или нулями — не
полагаться на них.

## Заголовок на USB

Перехват `usbmon` показал: в bulk-трафике **тоже нет заголовка** —
данные идут чистым потоком. Если бы заголовок был, SDK бы его срезал,
но для реверса протокола (см. `1.SDK/docs/PROTOCOL.md`) это значит:
`_INTER_CMD_HEAD` — только в командных пакетах, в видеопотоке его нет.
EOF
```

```bash
# Режимы потока и доступность raw-данных

## Что доступно через SDK

SDK отдаёт **один тип потока**: радиометрический Y16, после NUC и DPR.
Переключения режима через публичный API `USBSDK_*` нет.

## Проверка через V4L2

```
v4l2-ctl --list-devices
v4l2-ctl -d /dev/videoN --list-formats-ext
```

(вывод приложить при первом запуске)

Ожидаемо: камера видна как одно UVC-устройство, формат — Y16 или
YUY2/NV12 (после AGC драйвера).

## Данные до NUC — недоступны

**Доказательство из данных захвата:**

| Кадр | max raw | Комментарий |
|---|---|---|
| 0 | 56317 (462 °C) | «Голый» сенсор до NUC — hot pixel виден |
| 2 | 13406 (34 °C) | После NUC — выброс подавлен |
| 208–499 | ~13400 | Стабильно |

Если бы NUC не применялся, hot pixels присутствовали бы постоянно.
Они исчезают на кадре 2 — значит NUC применяется в FPGA до USB.

**Вывод: Y16 — после NUC.** Данные до NUC физически не покидают FPGA.

## Радиометрический Y16 — что с ним можно

1. **Измерение температуры** через `T = (raw - 10000) / div` — работает
   после калибровки (см. NETD_MRTD.md).
2. **NETD/MRTD** — измеримо, но с оговоркой: часть шума уже подавлена.
3. **Свой DDE/AGC/TNR** — полностью, на этих данных.

Что **нельзя**:
- получить шумовые характеристики «сырого» сенсора
- измерить реальный NETD микро-болометра
- работать с 14-битным АЦП до упаковки в 16 бит

## Замечание про периодические shutter'ы

В 500 кадрах обнаружено 3 shutter-события (кадры 128, 173, 206).
Между ними — стабильные участки по 40–290 кадров.

Для NETD-измерений использовать **только** самый длинный стабильный
сегмент (в нашем случае 208..499). Иначе drifts завышают шум в 10 раз.
EOF
```

```bash
cat > docs/NETD_MRTD.md << 'EOF'
# Оценка NETD по радиометрическому Y16

## Метод

NETD (Noise Equivalent Temperature Difference) — минимальная разница
температур, которую камера может различить. Формула:

```
NETD = σ_T   (при наблюдении однородного чёрного тела)
```

где `σ_T` — временной шум в единицах температуры.

Для Y16 с формулой `T = (raw - 10000) / div` (div = 100):
```
NETD = σ_raw / 100
```

Метод измерения:
1. Снять серию кадров на стабильной сцене (лучше — закрытый объектив,
   но сойдёт и однородный фон).
2. Отбросить кадры с shutter-событиями.
3. Взять самый длинный стабильный сегмент.
4. Для каждого пикселя вычислить `std` по времени.
5. Взять median (устойчиво к выбросам).

## Результат

**Файл:** `raw16.bin`, 500 кадров, `capture_raw 500`
**Стабильный сегмент:** кадры 208..499 (291 кадр, ~11.6 сек при 25 fps)

| Метрика | Значение |
|---|---|
| Temporal noise, median | 9.76 count |
| Temporal noise, mean | 18.71 count |
| Temporal noise, 90th percentile | 21.66 count |
| **NETD (по медиане)** | **98 mK** |
| NETD (по среднему) | 187 mK |
| NETD (по 90-му процентилю) | 217 mK |

## Оговорки

### 1. Это НЕ NETD сенсора

Y16 приходит **после NUC и DPR**. NUC подавляет low-frequency шум
(FPN, column noise). DPR заменяет битые пиксели. Реальный NETD
сенсора микро-болометра был бы **выше** (численно больше).

Наша оценка **98 mK** — это:
- **оптимистичный** NETD системы в текущей конфигурации
- **реалистичный** NETD для практических задач (детект объектов, измерение ΔT)

### 2. Разброс median vs mean

Median 9.76 count, mean 18.71 count. Разница **в 2 раза** означает:
- ~50% пикселей имеют шум ~10 count (хорошие)
- ~10% имеют шум >21 count (битые / с остаточным FPN)
- ~40% имеют шум между 10 и 21

Для точных измерений можно построить **карту шума** (per-pixel std) и
маскировать плохие пиксели. Это отдельная задача.

### 3. Влияние сцены

Измерение проводилось **не на чёрном теле**, а на комнатной сцене.
Возможные искажения:
- тепловые потоки от рук/тела оператора
- ИК-излучение от монитора, ноутбука, стен
- недостаточно однородный фон

Для точного NETD нужен **чёрный тело** (или закрытый объектив при
равномерной температуре FPA).

## Сравнение с рынком

| Камера | NETD (паспорт) |
|---|---|
| FLIR Lepton 3.5 | <50 mK |
| HIKMICRO Mini2 640 | <40 mK |
| Seek Compact Pro | <70 mK |
| Типичный microbolometer 17 µm | 40–100 mK |

**Наш результат (98 mK) — в рынке**, ближе к нижней планке китайских
модулей.

## Для MRTD

MRTD (Minimum Resolvable Temperature Difference) требует:
- коллиматора и 4-bar target (мирра Фуко)
- процедуры субъективной оценки
- серии измерений при разных пространственных частотах

Без оборудования **не измерить**. Может быть заменён на **MTF-анализ**
через наклонную щель или край, но это тоже отдельная задача.

## Что можно улучшить

1. **Повторить на чёрном теле** при 2 температурах — калибровка NETD.
2. **Построить карту шума** — маскировать плохие пиксели.
3. **Долгая серия** (10 000 кадров) — оценить низкочастотный дрейф.
4. **Сравнение с IRSDK_Frame2Gray_DDE_m_v3** — там свой TNR,
   который дальше давит шум. Оценить цену TNR в деталях.
EOF
```
