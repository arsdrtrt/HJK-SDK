# Режимы потока и доступность raw-данных

Результат исследования всех доступных путей доступа к данным сенсора:
через вендорский SDK и через стандартный V4L2 (uvcvideo).

## Сводная таблица

| Путь | Формат | Значения | Baseline | NETD (median) | Годится? |
|---|---|---|---|---|---|
| **SDK Y16** (`USBSDK_*`) | 16-бит raw | 12000..14000 | 10000 | 62 mK | ✅ основной |
| **V4L2 640×516** | 16-бит + meta | 4780..5310 | ~2300 (?) | **15.6 mK** | ⚠️ требует калибровки |
| V4L2 640×512 | YUYV 8-бит | 30..221 | — | — | ❌ превью |
| V4L2 640×1032 | = 2× 640×516 | — | — | — | ⚠️ два кадра пакетом |
| V4L2 640×517 | 16-бит + 5 строк meta | ? | ? | ? | ⏳ не проверено |

## 1. SDK Y16 — основной путь

**Источник:** callback `USBSDK_CreateCallBack` → `Frame::buffer`

**Структура:**
```
offset 0       : uint16[640×512] Y16 пикселей
offset 655360  : следующий кадр
```
Заголовка нет. Чистые пиксели row-major.

**Диапазон:** 12000..14000 (типично 12200..13600 в комнате)
**Baseline:** 10000
**Формула:** `T_°C = (raw - 10000) / 100`

**Шум (500 кадров на стабильной сцене):**
- temporal noise median: 6.22 count = **62 mK**
- temporal noise mean: 21.70 count = 217 mK
- temporal noise p90: 62.26 count = 623 mK

**Что это даёт:** радиометрический поток после NUC/DPR, стабильный,
стандартная формула перевода в °C. Готов к измерениям.

**Ограничения:** требует вендорский SDK + udev-правило для USB
(см. `1.SDK/docs/LIFECYCLE.md`).

## 2. V4L2 640×516 — 16-бит + UVC payload header

**Источник:** `/dev/video2` через `v4l2-ctl` / `libuvc`, формат `YUYV 640×516`

**Открытие:** этот формат отдаёт **16-битный поток**, а не 8-битное YUYV-превью.
Размер кадра `640×516×2 = 660 480` байт, из которых:
- `640×512×2 = 655 360` — пиксели
- `4×640×2 = 5 120` — метаданные (4 строки по 640 uint16)

**Диапазон пикселей:** 4780..5310 (типично 4800..5300)
**Baseline:** неизвестен, требуется калибровка (см. §2.2)

**Шум (100 кадров):**
- temporal noise median: **1.56 count = 15.6 mK**
- temporal noise mean: 3.78 count
- temporal noise p90: 2.55 count

**На чёрном теле (100 кадров):**
- temporal noise median: **1.08 count = 10.8 mK**

**Что это значит:** шум в **4× ниже**, чем у SDK Y16 (62 mK).
Это указывает на то, что **в V4L2-потоке уже применён TNR**
(temporal noise reduction) в FPGA. SDK, вероятно, отдаёт поток **до TNR**
(более «сырой»).

### 2.1. Структура UVC payload header

Метаданные — 4 строки × 640 uint16 = 5120 байт после пикселей.

**Row 0 — стабильная** (header, содержит размеры):
```
[2520, 1788, 0, 43, 19, 1, 0, 0, 512, 640, 164, 0, 0, 0, 0, 4]
  ↑     ↑                       ↑    ↑    ↑              ↑
  │     │                       │    │    │              └─ версия/флаг = 4
  │     │                       │    │    └─ 164
  │     │                       │    └─ width = 640
  │     │                       └─ height = 512
  │     └─ magic = 0x06FC
  └─ magic = 0x09D8
```
Не меняется между кадрами.

**Row 1 — стабильная** (расширенный header):
```
[52445, 43707, 198, 0, 640, 0, 512, 0, 19760, 0, 60000, 0, 0, 0, 0, 0]
  ↑      ↑                ↑    ↑    ↑        ↑
  │      │                │    │    │        └─ 60000 (600.00 °C? max диапазон?)
  │      │                │    │    └─ 19760 (197.60 °C? или offset)
  │      │                │    └─ height (32-бит) = 512
  │      │                └─ width (32-бит) = 640
  │      └─ magic = 0xAAB9
  └─ magic = 0xCCDD
```
Не меняется между кадрами.

**Row 2 — динамическая**, меняется редко (не каждый кадр):
```
frame 0:   [314, 28781, 29251, 27764, 8285, ...]
frame 1:   [30, 21327, 8260, 21061, ...]
frame 2-8: [30, 21327, 8260, 21061, ...]  ← одинаковые
frame 9:   [368, 24948, 27507, 25439, ...]  ← снова другое
```
Похоже на **состояние FPGA/калибровки**, не PTS.
Меняется пачками каждые ~8 кадров — возможно, обновление статистики
для AGC или внутреннего состояния.

**Row 3 — нули** (резерв).

### 2.2. Калибровка V4L2 → °C

**Формула SDK:** `T = (raw - 10000) / 100`

**Для V4L2** прямой формулы пока нет. Из сравнительного замера:

| Поток | mean (room scene) | first16 |
|---|---|---|
| SDK | 12377 | 12306 12306 12306 12293... |
| V4L2 | 4701 | 4702 4682 4687 4682... |

Разница `7676 count`. Отношение `2.633`.

**Линейная регрессия** (SDK = a·V4L2 + b) на **разных сценах**
(снимали в разное время, было движение) дала:
```
SDK = 1.3161 × V4L2 + 6188.7
residual: std=1238, max=43905  ← плохо
```

**Регрессия не сходится** потому что:
1. Снимали **в разное время** — сцена поменялась (человек двигался)
2. Диапазон V4L2 узкий (~100 count) — rank deficiency

**Что нужно для точной калибровки:**
- Снять SDK и V4L2 **на одном и том же стабильном объекте**
  (лучше — чёрное тело или закрытый объектив)
- Желательно — при 2 разных температурах
- Тогда `SDK = a·V4L2 + b` определится точно

### 2.3. Что можно делать с V4L2 640×516

**Плюсы:**
- **Работает без вендорского SDK** — достаточно uvcvideo
- **Не требует sudo** после добавления в группу `video`
- **Шум в 4× ниже** (уже прошёл TNR)
- **Метаданные о кадре** (размеры, magic, возможно температура)

**Минусы:**
- **Baseline и формула неизвестны** — нужна калибровка
- **Конфликтует с SDK** — нельзя одновременно
- **TNR уже применён** — для оценки NETD сенсора не годится
- Метаданные не задокументированы вендором

## 3. V4L2 640×512 — 8-битное YUYV-превью

**Источник:** `/dev/video2`, формат `YUYV 640×512`

**Размер кадра:** `640×512×2 = 655 360` байт

**Структура YUYV:**
```
байт 0: Y0 — яркость пикселя 0    (0..255)
байт 1: U  — цветовая разность     (всегда 0x80 = 128, серый)
байт 2: Y1 — яркость пикселя 1    (0..255)
байт 3: V  — цветовая разность     (всегда 0x80 = 128, серый)
...
```

**Значения:**
- Y: 30..221 (8-бит)
- U, V: 0x80 (константа, серый)

**Что это:** 8-битное grayscale-превью **после AGC**. Радиометрии нет.
Годится только для просмотра картинки, не для измерений.

## 4. V4L2 640×1032 — два кадра пакетом

**Размер кадра:** `640×1032×2 = 1 320 960` байт = **2 × 660 480**

Идентичен V4L2 640×516, но содержит **два последовательных кадра**.
Структура:
```
offset 0        : кадр N (640×516: 512 строк пикселей + 4 строки meta)
offset 660480   : кадр N+1 (640×516)
```

Это формат для стриминга с **высокой частотой** (60 fps?) или
packing для повышения эффективности USB.

## 5. V4L2 640×517 — не проверено

**Размер кадра:** `640×517×2 = 661 760` = 512 строк пикселей + **5 строк meta**.

Вероятно, расширенная версия 640×516 с дополнительной строкой метаданных.
**Требует отдельного исследования.**

## 6. Прочие форматы

Нестандартные разрешения в дескрипторе камеры:
- `YUYV 80×8221`
- `YUYV 332×991`
- `YUYV 512×1288`

Скорее всего — варианты упаковки одного и того же потока
(альтернативные layouts). Требуют проверки, но не приоритет.

## 7. Комбинированный стрим

`YUYV 640×1032` = два кадра подряд. Если камера отдаёт их с частотой
60 fps → на выходе 30 «двойных» кадров/с = 60 fps одиночных.

## 8. Данные до NUC — недоступны нигде

**Доказательство из SDK-захвата:**
| Кадр | max raw | Комментарий |
|---|---|---|
| 0 | 56317 (462 °C) | hot pixel — NUC не применён |
| 2 | 13406 (34 °C) | NUC применён |
| 208–499 | ~13400 | стабильно |

**Доказательство из V4L2-захвата:**
- диапазон 4780..5310 — узкий, hot pixels отсутствуют
- значит NUC/DPR применяется **до** V4L2-интерфейса

**Вывод:** NUC выполняется в FPGA на пути сенсор → USB.
Данные до NUC физически не покидают чип ни через SDK, ни через V4L2.

## 9. Периодические shutter-события

Наблюдались в SDK-потоке (500 кадров):
| Кадр | ΔT | Длительность |
|---|---|---|
| 128→129 | +2.1 °C | 44 кадра |
| 173→174 | +2.8 °C | 32 кадра |
| 206→208 | −4.9 °C | 2 кадра |

Период ~12 секунд. Механический затвор обновляет NUC, baseline сдвигается.
**Для измерений — только длинные стабильные сегменты** (208..499 в примере).

В V4L2 640×516 shutter-события **не детектировались** (jumps >50 count: 0
на 100 кадрах). Возможно потому, что TNR их сглаживает.

## 11. Приоритеты дальнейшего исследования

1. **Калибровка V4L2 640×516 → °C** — снять SDK и V4L2 на чёрном теле
   при 2 температурах, получить формулу `SDK = a·V4L2 + b`
2. **Расшифровка row 2 метаданных** — выяснить, что там меняется
3. **V4L2 640×517** — проверить 5-ю строку метаданных
4. **TNR: включён или выключен** — если V4L2 более «гладкий»,
   попробовать отключить TNR в SDK и получить NETD без фильтрации
5. **Собственный libuvc-клиент** — читать V4L2 640×516 без uvcvideo,
   напрямую через libusb bulk/isoch (см. `1.SDK/docs/PROTOCOL.md`)

## 12. Калибровка V4L2 → °C

Пиксельная регрессия SDK ↔ V4L2 на **одной статичной сцене** (200 кадров):
SDK = 1.2633 × V4L2 + 6092.3
T_°C = 0.012633 × raw_v4l2 − 39.0768

PCC = 0.968
residual std = 61.0 count (0.61 °C)
residual median= 23.7 count

**Проверка на средних:**
| Поток | mean | T °C |
|---|---|---|
| SDK | 12184 | 21.84 |
| V4L2 | 4822 | 21.83 |
| diff | — | −0.01 |

**Ограничения:**
- PCC < 0.99 — не идеально, потому что в SDK-серию попал shutter
- V4L2 temporal std = 0.96 count — поток уже прошёл TNR
- SDK temporal std = 176 count — shutter-дрейф во время съёмки

**Для повышения точности:** снимать **по 20 кадров** на статичной
сцене (быстрее shutter-события в 5.5 сек).

## 13. Практическое применение

Теперь **можно работать без вендорского SDK**:

```bash
# 1. Снять V4L2 640×516
v4l2-ctl -d /dev/video2 \
  --set-fmt-video=width=640,height=516,pixelformat=YUYV \
  --stream-mmap --stream-to=frame.bin --stream-count=1

# 2. Отрезать пиксели (первые 640×512×2 = 655360 байт)
head -c 655360 frame.bin > pix.bin

# 3. Применить формулу
python3 -c "
import numpy as np
d = np.fromfile('pix.bin', dtype=np.uint16).reshape(512, 640)
T = 0.012633 * d - 39.0768
print(f'T: min={T.min():.2f} max={T.max():.2f} mean={T.mean():.2f} °C')
"

Без udev-правила, без симлинков, без sudo, без вендорских DLL.
